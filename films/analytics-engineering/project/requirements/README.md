# Requirements

What people asked for, decided and found, kept with what it's about. Every question,
requirement, decision, gap and known limitation is an item in a register: one YAML file per
source, core domain and consumer, plus one for the project. They're gathered as the work goes,
at every step of [the process](../docs/process.md), and each item says which step it belongs to.

[`docs/registers.md`](../docs/registers.md) indexes every item, by type and by scope and step. It's
generated by `scripts/generate/registers.py`, which also checks every register against the schema
below. CI fails if a register is wrong or the index is out of date.

## Where an item goes

| Register | What it's about | Example |
|---|---|---|
| `_project__requirements.yml` | What every domain shares: keys, versions, layout, engines | DEC-PRJ-01, keys are qualified by their key set |
| `sources/<system>/_<system>__requirements.yml` | A source: what it holds, against what the business expects | GAP-LMS-01, no revocation flag |
| `models/<domain>/_<domain>__requirements.yml` | A core domain: what its entities mean, and how they're modelled | DEC-STU-01, a microcredential is a kind of credential |
| `exposures/<consumer>/_<consumer>__requirements.yml` | A consumer: its question, and what it needs from the output | Q-PLN-01, Planning's question |

The folders mirror `sources/`, `models/` and `exposures/`, so a domain that becomes its own project
takes its registers with it. An item about several sources goes in the register of the one it was
found in, or of the domain that owns the fix, and lists the others in `sources`.

## The schema

Each register names its scope, then lists its items:

```yaml
scope:
  kind: source            # project, source, domain or consumer
  name: learning_platform # the folder's name
  code: LMS               # the scope in each item's id

items:
  - id: GAP-LMS-01        # <TYPE>-<SCOPE>-<nn>
    type: gap
    step: gaps_and_contracts
    title: No revocation flag
    ...
```

| Field | Who has it | What it holds |
|---|---|---|
| `id` | every item | `Q`, `REQ`, `DEC`, `GAP` or `LIM`, the register's code, and a number: `DEC-STU-03` |
| `type` | every item | `question`, `requirement`, `decision`, `gap` or `limitation` |
| `step` | every item | The step of the process it belongs to: `scope`, `source_reality`, `consumer_output`, `gaps_and_contracts`, `tests`, `build`, `validate`, `review_and_ship`, `written_once` or `operate_and_evolve` |
| `title` | every item | One line |
| `status` | every item | `open`, `agreed`, `delivered` or `superseded` |
| `text` | every item | The question, the requirement, the decision, or a gap's resolution |
| `raised_by`, `owner` | questions, requirements; `owner` on gaps | Who asked, and who answers or decides |
| `decision` | questions | The decision the answer supports |
| `why`, `decided_by`, `decided_on` | decisions (`why` required) | |
| `expectation`, `reality`, `resolution` | gaps | What the business expects, what the source holds, and one or more of `fix_at_source`, `rule_in_model`, `accept` |
| `evidence` | optional | The queries that show it, in `analyses/` |
| `informed` | optional | Who must be told: the distribution list |
| `sources` | optional | Every source an item is about, when it's more than its own |
| `relates_to` | optional | Other items' ids; the script checks they exist |
| `implemented_in` | optional | The models, tests, seeds, macros or exposures that carry it out |

## Adding an item

1. Find its register: the source, domain or consumer it's about. A new source, domain or consumer
   gets a new register, in a folder named like its folder in `sources/`, `models/` or `exposures/`.
2. Give it the next number in that register, its step and `status: open`.
3. Run `python scripts/generate/registers.py`, and commit the register and the index together.
4. When it's agreed or delivered, change its status. Don't delete a superseded item: mark it
   `superseded`, and point to what replaced it with `relates_to`.

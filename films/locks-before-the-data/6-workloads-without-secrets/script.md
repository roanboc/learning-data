## The promise

Every line passes two tests: anyone who has ever scheduled a job can follow it, and a platform engineer finds nothing wrong in it. In the Netherlands of the 1990s a car started for anyone who could close its ignition switch, with a wire or a copied key, until every new car asked a chip in its key for a code before the engine would run, and car theft fell by about 40 percent. A job can be asked the same way: it proves who it is each time it runs, and nothing it carries would work for anyone else. So the nightly job gets a name of its own in Microsoft Entra ID; Azure Databricks runs it as itself; its deploy signs in from GitHub Actions with a note GitHub signs for that one run; Azure resources sign in as managed identities; tools reach GitHub through an app instead of a person's token; the one password nothing else can replace yet waits in one vault, changed by a machine; and the copies already made are found and made worthless. **A workload proves who it is without a password.**

## The story in one paragraph

The Netherlands, in the middle of the 1990s. Cars stand in every street, and every year about one in two hundred is stolen: the ignition lock only turns a switch, and a wire behind the steering wheel closes it too, as does a copied key. For the owner, that's a morning with no car, no way to work, a claim to make, and a car that may never come back. In 1995 the European Union decides that from October 1998 every new car sold must have an electronic immobiliser: a small chip in the key, which the car asks, by radio, for its code; without the right answer, the engine won't run, and a wire or a key cut to the same shape starts nothing. In the Netherlands new cars with one go from about one in five in 1994 to all by 1998, car theft falls by about 40 percent, for no more than €50 a car, and far fewer owners wake to find their car gone. At the university, the job that loads the registrar's records every night at two already has a name of its own, `registrar-loader`, but still runs on Jun Park's personal token, made on 14 March 2024 with no end date and copied into the job's settings, a notebook in GitHub and Jun's laptop: like a car without an immobiliser, it starts for anyone with a copy. Sam Okafor makes the job a service principal in Microsoft Entra ID, which he owns and Azure Databricks reads, the only member of the group that owns the registrar's catalog; sets the job to run as itself; and takes the token out of its settings. On Tuesday 20 October the load runs under its own name. Its deploy moves from Jun's laptop to GitHub Actions, which keeps no token: for every run GitHub signs a short note, this repository, this environment, now, and Azure Databricks gives the run a pass for an hour only when the note says exactly what `registrar-loader`'s policy names; a copy run anywhere else gets no pass. Azure resources get managed identities, whose credentials nobody sees; Git folders reach GitHub through the Databricks GitHub app, not people's tokens. One door still wants a password, the student system's, so it lives in one key vault, readable only by `registrar-loader` and changed each month by a function that signs in as its own managed identity, the exception written down. On Tuesday 3 November secret scanning reads the repository's whole history and finds Jun's token, still working; Jun ends it, the copies open nothing, push protection stops the next secret at the door, and that afternoon personal tokens are switched off. Like the car asking its key, the platform asks each run who it is, and a copy can't answer.

**Where the film differs, on purpose.** It doesn't teach OAuth flows, token formats or claims beyond the three a check needs (the repository, the environment, the time), and it builds no certificate: nothing in the university's story needs rung three, so the film says nothing about it. It calls a token's exchange "a pass" and GitHub's OpenID Connect token "a note", the ideas film's words, and uses the docs' names for products and settings on screen.

**Practice.** What practitioners recognise: a scheduled job on someone's personal token because that was the quickest way to start; deploys from one person's laptop; people's own tokens behind every Git connection; a token found in a repository's history years after it was pushed, still working; a vault opened with a secret kept somewhere else, so the problem only moves; a password rotated by a script that holds another password; an exception nobody looks at again. And what works: every new job starts as a service principal with an owner; deploys sign in by federation, with the subject pinned to one repository and environment; resources get managed identities; a secret stays only where nothing else works, in one vault, rotated by a machine, with a written exception; and a leaked secret is ended first, then cleaned up.

**The author's practice** (3 November 2026): "the preferred use of passwordless authentication, so secrets don't need to be managed by people, similar to workspace identities in Fabric instead of using service accounts". The film says it in its own words: "Now the platform knows which job it is, and gives each run its way in, with nothing anyone keeps."

## Rigour to check before recording

Checked on 5 November 2026, and GitHub's list of supported secrets again on 10 November 2026; the sources are listed below.

- **Car theft in the Netherlands.** About one car in two hundred stolen a year in the middle of the 1990s; the electronic immobiliser required in every new car from 1 October 1998; in the Netherlands, new cars with one going from about 20 percent in 1994 to all of them by 1998; car theft about 40 percent lower over the following years because of it; at most about €50 a car (van Ours and Vollaard, *The Economic Journal*, 2016, which studies the Netherlands from 1995 to 2008). "A wire behind the steering wheel can close it too, and so can a copy of the key" is hot-wiring and a key cut to shape, the two ways the paper's era of theft worked; the film doesn't follow later ways round immobilisers, since its point is what asking the key changed. The owner and her morning are an invented composite: the paper counts thefts, not owners.
- **The rule.** Commission Directive 95/56/EC of 8 November 1995, adapting Council Directive 74/61/EEC on devices to prevent the unauthorised use of motor vehicles, made an electronic immobiliser compulsory for new passenger cars entering service from 1 October 1998. The card names it; the narration says "from October 1998, every new car sold must have an electronic immobiliser".
- **How the immobiliser asks.** A transponder chip in the key's head; a coil round the ignition lock powers it by radio and reads its code; the engine's control unit lets the engine run only on the right code, so closing the switch with a wire, or turning a key cut to the same shape without the chip, starts nothing. Later systems ask a fresh question each time and check the answer, which the film's question and answer also fits.
- **The job, its people and its numbers.** `registrar_nightly_load` at 02:00; Jun Park's personal token, made 14 March 2024 with no end date; the job's identity `registrar-loader`, owned by Sam Okafor; the group `registrar_owners` (*Grants by design*'s), which owns the registrar's catalog (the module's `numbers.md`; *Who is it, really?* and *No secret to lose*). The three copies are *No secret to lose*'s: the job's settings, an old notebook (here, in GitHub, pushed in March 2024) and Jun's laptop, from which he deployed each change. On the platform the module builds on, new personal tokens have had at most two years' life since December 2024, so a token with no end date is older (Azure Databricks release notes, December 2024).
- **The dates**, agreed with *People and groups* and *Who did what*: Monday 19 October 2026, 02:00, the last run on Jun's token (its "last used" on his tokens page); Tuesday 20 October, 02:00, the first under `registrar-loader`; Tuesday 3 November, Secret Protection on, the token found and ended by Jun that morning, "two weeks" after its last use; that afternoon personal tokens switched off on the platform (*People and groups*). Jun ends his own token, as anyone may; ending someone else's is an admin's power, which *Power you switch on* keeps switched off.
- **A service principal.** Microsoft Entra ID: an application's identity in a tenant, used by workloads; owners can be set. Azure Databricks: "an identity that you create in Azure Databricks for use with automated tools, jobs, and applications"; service principals managed in Microsoft Entra ID are read into the account with people and groups by automatic identity management (*People and groups* shows it). "Its rights come from a group": `registrar-loader` is the only member of `registrar_owners`, and grants go to the group (*Who is it, really?*).
- **Run as.** A job's *Run as* setting can name a service principal, which a job's owner may set with the service principal's *User* role; the job then runs with the service principal's rights, and the platform gives each run its own short-lived credentials, which nobody handles ("gives each run its way in, with nothing anyone keeps"). Jun's token in the job's settings was a parameter the job's notebook used to call the platform; the film shows it taken out.
- **Federation for the deploy.** Azure Databricks' workload identity federation for GitHub Actions: a federation policy on the service principal, in the account console, names the issuer (`https://token.actions.githubusercontent.com`), the audience and the subject, here `repo:uni-example/data-platform:environment:production`; the workflow has `permissions: id-token: write` and `DATABRICKS_AUTH_TYPE: github-oidc`, and the Databricks CLI fetches GitHub's token and exchanges it for a Databricks OAuth token. "Each access token is valid for one hour" (Databricks' OAuth pages), so "good for an hour". GitHub issues a token to any job that asks, in any repository; its subject says which repository and environment, which is why a copy elsewhere gets a token "that says where, and no pass". The page's rows (organization, repository, entity type, environment) are the console's fields for a GitHub Actions policy, which make that subject. The film assumes, as the docs don't forbid, that a federation policy can sit on a service principal that comes from Microsoft Entra ID.
- **"The note is good for minutes."** GitHub's OpenID Connect token is short-lived; the reference's example token expires minutes after it's issued; it's made for one job's run and kept nowhere. "Nothing is stored in GitHub to steal": no secret in the repository's or environment's secrets.
- **Azure.** Microsoft Entra ID's federated identity credential, scenario *GitHub Actions deploying Azure resources*, names the organization, repository, entity type and environment, and Azure's sign-in action exchanges the same kind of token. The page shows it on `registrar-loader`'s registration; what that sign-in may change in Azure is whatever roles the identity holds there, which the film doesn't show. Who may deploy to production and who approves is *From a branch to production*'s.
- **Managed identities.** "You don't need to manage credentials. Credentials aren't even accessible to you" (Microsoft Learn, *What are managed identities for Azure resources?*): "nobody ever sees them"; Azure rotates them. The catalog's access connector for Azure Databricks uses its managed identity to reach storage for Unity Catalog; *Network, storage and keys* makes it the only standing identity on the registrar's files, with a raised admin account reaching them only for a task (*Power you switch on*). The rotation function's own identity is the same idea.
- **Git folders and the Databricks GitHub app.** Git folders can link to GitHub with a person's token or through the Databricks GitHub app, installed on all or only chosen repositories, which acts for each person; its "access tokens expire after 8 hours" and are refreshed for them (Azure Databricks, *Configure Git credentials*). GitHub's guidance is to use a GitHub App with fine-grained permissions on chosen repositories rather than a person's token for tools and integrations; GitHub Apps for workflows aren't needed by this story and aren't shown.

An Azure Key Vault-backed secret scope, `student-system`, readable by `registrar-loader` alone through the scope's permissions. Azure Databricks redacts secret values read with `dbutils.secrets.get` when they're printed, as `[REDACTED]`; the docs warn that redaction isn't a boundary against someone set on getting the value out, so the film says only "by mistake".
- **Rotation.** Key Vault's rotation tutorial changes a secret with an Azure Function that signs in to the vault with its managed identity, sets the new value at the resource and stores it in the vault; the film's function, `registrar-rotate`, runs on the first of each month, its period the film's example. The student system is unnamed and no product; it takes only a password. - **Secret Protection.** GitHub Secret Protection, bought for the repository (the university is on GitHub Enterprise Cloud, *Who did what*), brings secret scanning and push protection. "Secret scanning scans your entire Git history on all branches present in your GitHub repository"; for a Databricks API Token it alerts, offers push protection and checks validity (*Supported secret scanning patterns*, read 10 November 2026: "Databricks API Token", `databricks_access_token`), which the alert shows as active or inactive; an alert can be closed as "Revoked". The file `registrar/notebooks/check_load.py` is the film's.
- **The history.** Once the token is ended, the copy in the history opens nothing; rewriting a shared repository's history would break everyone's copies of it and wouldn't reach the copies already made, so the film leaves it, and says so.
- **Push protection.** It blocks a push that contains a supported secret before it lands; a person can bypass it by choosing a reason, and the bypass creates an alert that organization owners, security managers and repository administrators can be told about ("the platform team gets an alert"). Delegated bypass, which needs an approver, isn't shown.
- **Personal tokens switched off.** A workspace admin can stop people making personal access tokens (Azure Databricks, *Monitor and revoke personal access tokens*); *People and groups* does it that afternoon.

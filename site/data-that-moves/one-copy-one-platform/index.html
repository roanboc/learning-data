One copy, one platform: a claim written once, read by all

At the university, tutors' claims went round by email, and payroll and Finance each kept a copy that never quite agreed. The new claims app writes each claim once, on Lakebase, and payroll, the claims job and Finance read that same row through Unity Catalog. No pipeline, no second platform.

Go further in the official docs

The film shows the idea once. The docs say how one copy of the data serves both transactions and analysis, which system writes each table, and how to set each path up.

  • LTAP architectureOne copy of the data under one governance, with purpose-built engines for transactions and analysis, and a single writer for each table.
  • Lakebase PostgresThe Postgres database in Databricks that the claims app is built on.
  • Register a Lakebase database in Unity CatalogHow the lakehouse reads the app's own rows, with the permissions, lineage and audit of every other table.
  • Serve lakehouse data with synced tablesHow the lakehouse serves a table it writes, such as the contracts, to an app that reads it.
